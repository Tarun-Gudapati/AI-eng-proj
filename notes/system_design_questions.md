# System design question bank: small to big

How to use this: answer out loud first, then check the short answer.
Every answer should cover four things: what it is, when you use it, what breaks, and the trade-off.
Tick a question only when you can answer it in under a minute without notes.

---

## Level 1: tables and data

**1. Primary key or unique constraint: what's the difference?**
Both stop duplicates. A table has one primary key; it identifies the row, can't be NULL, and is usually the clustered index.
A table can have many unique constraints for other "never twice" rules, such as `vehicle_number`.

**2. Why put rules (`NOT NULL`, `CHECK`, `UNIQUE`) in the database, and not only in code?**
Code has bugs, and there is more than one way in: other services, scripts, manual fixes. The database is the last line of defence,
and its rules hold even under concurrency. Today you saw it: without `NOT NULL`, a ride with no rider got in.

**3. What does a foreign key protect you from?**
Orphans: a ride pointing to a rider who doesn't exist, or deleting a rider who still has rides.
The trade-off is a small cost on every insert and delete, and you must create and drop tables in the right order.

**4. What is an index, and what does it cost?**
A sorted lookup structure, so the database doesn't scan the whole table. Reads get faster; every insert or update gets slightly slower,
and it uses storage. Index the columns you filter and join on, not every column.

**5. When would you use a filtered index?**
When a rule or query applies to only some rows. For example, "a driver has at most one active ride" is unique on `driver_id`
only where the status is Accepted or Ongoing. Completed rides don't count.

**6. Why not store the ride status on the Rider table as well?**
It's the same fact in two places, so every change has to update both, and one day they'll disagree.
Store each fact once (normalisation), and look up the rest with a query.

**7. `IDENTITY` int or GUID for keys?**
`IDENTITY`: small, fast, readable, but generated by the database and guessable.
GUID: can be created anywhere (useful across services or offline), but bigger, and random GUIDs fragment the index.

**8. Why `datetime2` and UTC?**
`datetime2` is more precise and is the modern type. UTC avoids time-zone and daylight-saving bugs; convert to local time only for display.

## Level 2: concurrency

**9. What is a race condition? Give an example.**
The result depends on timing. Two drivers both read "Requested" before either one writes, and both are told they got the ride.

**10. What is a lost update?**
Two writers read the same value, and the second write overwrites the first without knowing about it. The first change is lost.

**11. How does a conditional update stop the race?**
The check goes inside the `WHERE`, so checking and writing are one atomic step. The rows affected tell you who won: 1 means you, 0 means someone else.

**12. Optimistic or pessimistic concurrency?**
- **Optimistic:** don't lock; detect a conflict at write time (a version or `rowversion` column, or a conditional `WHERE`). Best when conflicts are rare.
- **Pessimistic:** lock first (`UPDLOCK`), and others wait. Best when conflicts are common. It costs waiting and risks deadlocks.

**13. What is a transaction? Explain ACID in one line each.**
A group of changes that succeed or fail together.
- **Atomic:** all or nothing.
- **Consistent:** rules (constraints) hold afterwards.
- **Isolated:** concurrent transactions don't see each other's half-done work.
- **Durable:** once committed, it survives a crash.

**14. What problems do isolation levels prevent?**
- Read committed stops dirty reads (reading uncommitted data).
- Repeatable read also stops a row changing between two reads.
- Serializable also stops phantoms (new rows appearing).
- Snapshot gives you a consistent picture without blocking readers.

Stronger isolation means more blocking or more conflicts.

**15. What is a deadlock, and how do you avoid one?**
Two transactions each hold a lock the other needs, so both wait forever, and SQL Server kills one (error 1205).
Avoid it by taking locks in the same order everywhere and keeping transactions short. Retry on 1205.

**16. Why does a C# `lock` fail once you have 3 servers?**
A `lock` only works inside one process. Each server has its own lock, so the race comes back.
Use the database (a conditional update or constraints) or a distributed lock, such as in Redis.

## Level 3: reliability

**17. What is idempotency, and what is an idempotency key?**
Doing the same request twice has the same effect as doing it once. The client sends a unique key with the request,
and the server stores it and ignores repeats. This fixes double taps and retries creating two rides.

**18. When do you retry, and how?**
Retry temporary failures: timeouts, 429, 503, 5xx. Never retry 400s. Use exponential backoff plus jitter, with a maximum number of attempts.
Only retry operations that are idempotent.

**19. At-least-once delivery: what is it, and why does it need idempotent consumers?**
The message is delivered one or more times, never lost, but sometimes duplicated. The consumer must handle duplicates safely.
"Exactly once" in practice means at-least-once plus an idempotent consumer.

**20. What problem does the outbox pattern solve?**
"Save to the database, then publish a message" can half-fail: the save works and the publish doesn't.
Write the message to an outbox table in the **same transaction**, and a worker publishes it later.

**21. What is a dead-letter queue?**
A place for messages that keep failing (poison messages), so they don't block the queue. Someone inspects them and fixes or replays them.

## Level 4: building blocks at scale

**22. Vertical or horizontal scaling? Why "stateless"?**
Vertical means a bigger machine; it's simple, but has a ceiling. Horizontal means more machines; it needs stateless services,
meaning no user state kept in server memory, so any server can handle any request.

**23. What does a load balancer do?**
It spreads requests across servers, stops sending traffic to unhealthy ones, and can end TLS. It removes one point of overload.
The load balancer itself must be redundant too.

**24. Cache-aside: how does it work, and what breaks?**
Read the cache; on a miss, read the database and fill the cache with a TTL. What breaks: stale data after an update
(invalidate on write), a stampede when a hot key expires, and the database getting flooded when the cache goes down.

**25. Redis for driver locations: is it a cache?**
No. There, Redis is the **primary store** for live data, overwritten every few seconds and expired when the driver goes offline.
A cache is a copy of data whose real home is somewhere else.

**26. Read replicas: what's the catch?**
Replication lag. You write to the primary, read from a replica, and don't see your own write yet.
Read your own writes from the primary when it matters.

**27. Sharding: how do you choose the partition key?**
Pick a key that spreads load evenly and keeps the data you query together, such as by city for rides.
Avoid hot keys. Queries that span shards become expensive.

**28. A simple queue or Kafka?**
- **Queue** (Service Bus): each message is handled once by one consumer. Good for tasks.
- **Kafka:** a durable log that many consumers read independently, and can replay. Good for high-volume event streams, such as location updates.

**29. WebSockets, polling, or push notifications?**
- **Polling:** simple, but wasteful and delayed.
- **WebSockets:** a live two-way connection, fast. You must manage connections at scale.
- **Push notifications** (FCM, APNs): reach phones that are asleep or offline. Use them as a fallback.

**30. CAP in plain words**
When the network splits, choose: stay **consistent** (refuse some requests) or stay **available** (answer, possibly with stale data).
Bookings choose consistency; driver locations choose availability.
